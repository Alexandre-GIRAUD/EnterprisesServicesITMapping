# AGENTS.md

Two workflow paths for this repo: **Feature workflow** (new work) and **Bug fix workflow** (fixing existing behaviour). Skills live under `.agents/skills/<name>/SKILL.md`. Project rules live under `.cursor/rules/` (`dev-standards`, `code-readability`).

**Language:** all output, code, comments, commits, and PR descriptions must be in English.

**Checkpoint commits:** keep commits granular for easy revert (see `.cursor/rules/workflow-commits.mdc`). At least **one commit per feature**; prefer **one commit per logical change** and one after each green workflow step. If several features are requested together, finish and commit feature A fully before starting feature B — never mix features in one commit. Skip only when a step produced no file changes.

## Domain modeling (run once per domain area, not per feature)

Before defining or modifying the data model (SI mapping entities: applications, interfaces, flows, hosting, etc.), run domain-modeling to sharpen the domain vocabulary and produce or update CONTEXT.md / ADRs. This ensures every future feature and every agent working on the data model uses consistent banking-IT terminology instead of inventing its own.

This step is not part of the per-feature loop — it's triggered manually when the domain model itself is being introduced or changed, not for every PR.

See `.agents/skills/domain-modeling/`.

A bug fix skips **to-spec** and **domain-modeling** — those apply to new work, not to fixing existing behaviour.

## Feature workflow

### 1. grill-me

Clarify requirements before any code is written.

**Done when:** requirements are sharp enough to implement; no coding has started.

### 2. to-spec

Turn the clarified conversation from grill-me into a published, versioned spec document before any code is written. This spec is what tdd and implement-spec will be implemented against, and what code-review will check compliance against later. See `.agents/skills/to-spec/`.

Store it in the location this skill defaults to (the project issue tracker from `docs/agents/issue-tracker.md`; for the local Markdown tracker that is `.scratch/<feature-slug>/spec.md`). Reference its path in the PR description generated by open-pr.

**Done when:** the spec is published at that path/URL; no coding has started.

### 3. tdd

Write failing tests first against the published spec (mandatory for every feature and fix — see `.cursor/rules/dev-standards.mdc`).

**Done when:** tests exist, fail for the right reason, and lock the intended behaviour from the spec.

### 4. implement-spec

Implement the feature to make the tests pass, against the published spec. Follow `.cursor/rules/code-readability.mdc`.

**Done when:** the new tests pass and the change matches the published spec.

### 5. security-secrets-scan

Run after every commit during implementation. See `.agents/skills/security-secrets-scan/`.

**Done when:** result is `clean`.

### 6. visual-verification

For any UI-facing change. See `.agents/skills/visual-verification/`. Skip only when the change has no UI surface.

**Done when:** verdict is `pass` (or skipped with an explicit non-UI reason).

### 7. code-review

Three-axis review: coding standards, spec compliance (against the published to-spec document), and readability. See `.agents/skills/code-review/`.

**Done when:** all three axes are reported and blocking findings are resolved.

### 8. dead-code-check

Must return `clean`. See `.agents/skills/dead-code-check/`.

**Done when:** result is `clean`.

### 9. Fix loop (steps 5–8)

If any check in steps 5–8 fails: go back to step 4, fix, and re-run the failed checks.

- **Maximum 3 total attempts** (the first run counts as attempt 1).
- If still failing after 3 attempts: **STOP** and escalate to the human developer with a summary of what failed and why — do not attempt a 4th cycle.

**Done when:** steps 5–8 all pass within 3 attempts, or the human has been escalated to.

### 10. open-pr

Once all checks pass, run `.agents/skills/open-pr/`: rebase on main, retest, final secrets scan, PR description (including the published spec path from step 2), open PR.

**Done when:** the PR URL is returned to the human.

### 11. Stop after opening the PR

The agent stops after opening the PR. Merging into main is always done manually by a human — the agent must never merge.

### 12. After merge (human)

After the human merges, the agent may run `.agents/skills/resolving-merge-conflicts/` if needed, then delete the feature branch.

**Done when:** conflicts resolved (if any) and the feature branch is deleted.

## Bug fix workflow

Separate path for fixing existing behaviour. Skips **to-spec** and **domain-modeling** — those apply to new work, not to fixing existing behaviour.

### 1. diagnosing-bugs

Diagnose the root cause before touching any code. See `.agents/skills/diagnosing-bugs/`.

**Done when:** root cause is identified; no fix code has been written yet.

### 2. Write a failing regression test that reproduces the bug

Mandatory TDD for fixes (see `.cursor/rules/dev-standards.mdc`).

**Done when:** a test fails specifically because of the bug.

### 3. Fix the bug to make the test pass

Follow `.cursor/rules/code-readability.mdc`. Change only what the root cause requires.

**Done when:** the regression test passes and no unrelated behaviour is broken.

### 4. security-secrets-scan

See `.agents/skills/security-secrets-scan/`.

**Done when:** result is `clean`.

### 5. code-review

Standards + readability. Spec compliance is not applicable for a pure bug fix unless the bug reveals a spec gap — then note the gap and review against it. See `.agents/skills/code-review/`.

**Done when:** standards and readability are clear; spec axis skipped or addressed if a gap was found.

### 6. dead-code-check

Must return `clean`. See `.agents/skills/dead-code-check/`.

**Done when:** result is `clean`.

### 7. Fix loop (steps 4–6)

Same retry limit as the feature workflow: if any check in steps 4–6 fails, go back to step 3, fix, and re-run the failed checks.

- **Maximum 3 total attempts** (the first run counts as attempt 1).
- If still failing after 3 attempts: **STOP** and escalate to the human developer with a summary of what failed and why — do not attempt a 4th cycle.

**Done when:** steps 4–6 all pass within 3 attempts, or the human has been escalated to.

### 8. open-pr

Same rules as the feature workflow: run `.agents/skills/open-pr/` (rebase, retest, final secrets scan, PR description, open PR). Never auto-merge. The agent stops after opening the PR; merging is always a manual human action.

**Done when:** the PR URL is returned to the human.

## Hard gates

| Gate | Skill / rule | Feature | Bug fix | Proceed only if |
|---|---|---|---|---|
| Spec | `to-spec` | yes | skip | published path/URL exists before code |
| Domain | `domain-modeling` | when model changes | skip | CONTEXT.md / ADRs current for the area |
| Secrets | `security-secrets-scan` | yes | yes | `clean` |
| UI | `visual-verification` | when UI | if UI affected | `pass` (or non-UI skip) |
| Review | `code-review` | yes | yes | standards + readability clear; spec when applicable |
| Dead code | `dead-code-check` | yes | yes | `clean` |
| Ship | `open-pr` | yes | yes | opens PR; never merges |
